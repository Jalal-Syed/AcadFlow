# ADR: Native Capacitor Plugin for Android Portal Capture

- Status: Accepted
- Date: 2026-09-17
- Decision owners: AcadFlow maintainers

## Context

AcadFlow imports attendance, marks, and subject data from college portals. The capture flow must let a user:

1. Open a portal inside the application.
2. Log in and navigate through redirects and portal pages.
3. Tap an AcadFlow-provided Capture button injected into the portal page.
4. Extract the page's HTML tables without sending portal credentials or page data to a third party.
5. Return a small, structured payload to the React application.
6. Parse the payload locally with the existing DOM table parser and save the result to the cloud-first data layer.

The desktop Electron implementation already provides a browser window, JavaScript injection, and an IPC callback. Android did not have an equivalent. `@capacitor/browser` opens a Custom Tab, but it does not provide reliable post-navigation JavaScript injection or a message bridge from the opened page. An external browser also cannot safely return captured DOM data to the app.

The existing parser in `src/lib/scraper/ai-extractor.ts` is now a deterministic `DOMParser` implementation. It does not require Ollama, WebLLM, an inference model, or a network service. The missing Android capability is therefore browser automation and transport, not extraction.

The generated `android/` project is ignored by Git and recreated in CI with `npx cap add android`. Native changes placed only in that directory would be lost on every clean build.

## Decision

Implement a tracked local Capacitor plugin at `plugins/portal-capture`.

The plugin will expose a small API to JavaScript:

- `PortalCapture.open({ url })`: opens a native Android WebView dialog.
- `PortalCapture.close()`: closes the dialog and cancels the active capture.
- `PortalCapture.addListener('capture', listener)`: receives `{ url, title, tables }`.
- `PortalCapture.addListener('closed', listener)`: receives a close event.
- `PortalCapture.addListener('error', listener)`: receives a user-safe error message.

The Android implementation will:

- Use a native `WebView` inside a modal dialog owned by the Capacitor activity.
- Enable JavaScript, DOM storage, and cookies required by normal portal login flows.
- Use `WebViewClient.onPageFinished()` to inject the Capture script after every navigation.
- Expose a narrowly scoped `@JavascriptInterface` named `AcadFlowCapture`.
- Receive only the capture payload generated by the injected script.
- Close the dialog after a successful capture and emit the payload to React.
- Enforce a ten-minute timeout and provide a visible close control.
- Keep the portal inside the app process; credentials are never read by the plugin.

The existing `INJECT_CAPTURE_BUTTON` script will be shared by Electron and Android. On Android, the script will call the native bridge method in addition to storing the payload in the page. The React layer will pass the received payload to `parseCapturedTables()` and then to the existing save/sync flow.

The Electron path remains unchanged. Web/PWA remains unsupported because it cannot provide the same embedded capture boundary. Android becomes supported only when the native plugin is available.

## Security and privacy constraints

- Do not log portal URLs, HTML, credentials, cookies, or captured table contents.
- Do not expose arbitrary native methods to page JavaScript.
- Accept payloads only from the active WebView and validate that the payload is a JSON object with bounded string fields before emitting it.
- Limit captured HTML size to prevent accidental memory abuse.
- Do not inject scripts into the main AcadFlow WebView; injection is limited to the portal WebView.
- Do not persist portal cookies or captured HTML in the plugin. WebView cookies are cleared when the capture dialog closes.
- Keep `addJavascriptInterface` limited to the single capture callback. Never expose an object with filesystem, reflection, or general-purpose evaluation methods.

## Alternatives considered

### `@capacitor/browser`

Rejected. It uses the platform browser/custom tab and exposes only open, close, and coarse page lifecycle events. It cannot inject the Capture button into subsequent portal pages or return table HTML.

### Community InAppBrowser plugin

Rejected as the primary foundation. The previously considered package was unavailable or did not provide a stable Capacitor 6 API with the required script injection and message behavior. The capture feature is central enough that an uncontrolled plugin dependency would create avoidable release risk.

### External browser plus deep link

Rejected. A deep link can return a URL, but not arbitrary authenticated DOM contents without creating a separate hosted capture service and introducing credential/data privacy concerns.

### Android source directly inside `android/`

Rejected. The directory is generated and ignored. CI would discard the implementation when `npx cap add android` recreates the project.

### Requiring users to copy and paste portal data

Rejected as the default. It is less reliable across portal formats and creates a poor mobile workflow, although it remains a possible future fallback.

## Consequences

### Positive

- Android capture uses a controlled, first-party WebView boundary.
- No model download, AI provider, portal proxy, or capture backend is required.
- The deterministic parser is shared across Android and desktop.
- The native implementation is tracked and survives clean CI builds.
- Authentication remains user-driven inside the portal WebView.

### Negative

- The project now owns a small amount of Android-native code and must test it on real devices.
- Some portals may block WebViews, require external browser authentication, or use cross-origin iframes whose contents cannot be read by page JavaScript.
- Android cookies and WebView behavior can vary by device and WebView version.
- The generated Android project must still be created and synced before building.

## Rollout and verification

1. Build the local plugin before `npx cap sync android`.
2. Install the debug APK on an Android device or emulator.
3. Verify login, redirects, back navigation, page reinjection, Capture button behavior, and close/timeout behavior.
4. Verify attendance, marks, and subjects each produce a parser result.
5. Verify captured data is saved to Supabase and the local cache only after the parser succeeds.
6. Verify Android CI builds the plugin, syncs Capacitor, assembles the APK, and uploads it.

## Failure behavior

If the native plugin is unavailable or a portal cannot be captured, Portal Sync must show a clear unsupported/error state. It must not show an AI model download requirement or leave the user waiting indefinitely.
